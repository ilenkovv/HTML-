# Application Configuration Module

Этот модуль реализует следующий продуктовый этап Web Master: настройку базы данных, пользователей, ИИ, административной панели и дашборда без необходимости проектировать PostgreSQL вручную.

## Пользовательский поток

После шага «Проверка кода» появляется шаг «Настройка приложения».

Основные переключатели:
- База данных
- Несколько пользователей
- ИИ
- Панель администратора

При выключенных функциях пользователь может сразу продолжить размещение обычного HTML/ZIP.

## Поля

Каждое поле имеет:
- тип данных;
- required/unique;
- принадлежность пользователю;
- признак чувствительных данных;
- режим доступа ИИ: none/read/write/read_write;
- источник detected/manual/system.

Секретоподобные поля (`password`, `token`, `cookie`, `api_key`, `private_key` и т.п.) автоматически исключаются из доступа ИИ.

## Связи

Поддерживаемые виды: one_to_one, one_to_many, many_to_many. В UI они должны отображаться обычными фразами, например «Один клиент может иметь много заказов».

## Многопользовательский режим

По умолчанию создаются роли:
- Владелец
- Администратор
- Пользователь
- Наблюдатель

Базовый режим регистрации — только по приглашению. Открытая регистрация должна включаться владельцем явно.

## Данные приложения

Миграция `20260901_app_runtime_config.sql` добавляет:
- `app_runtime_configs` — версионируемая конфигурация;
- `app_members` — участники приложения;
- `app_records` — универсальные записи сущностей;
- `app_record_links` — связи записей;
- `app_audit_log` — журнал действий;
- `app_daily_metrics` — агрегаты для дашборда.

RLS включён, но direct-client policies намеренно не создаются. Текущий пилот должен обращаться к таблицам только через server-side service role. Перед прямым клиентским доступом необходима отдельная auth/RLS модель.

## Важный архитектурный принцип

Конфигурация, пользователи и бизнес-данные не относятся к конкретной версии загруженного HTML/ZIP. Обновление приложения меняет код, но не удаляет `app_runtime_configs`, `app_members`, `app_records` и AI dataset.

## Следующий интеграционный шаг

1. Встроить `AppSetupPanel` в основной мастер после code check.
2. На анализе HTML/ZIP извлекать form/input/select/textarea и localStorage keys в `DetectedFieldCandidate`.
3. Сохранение конфигурации делать server-side с проверкой `validateAppConfig`.
4. Сгенерировать runtime API CRUD для `app_records` с permission checks через роль пользователя.
5. Подключить Supabase Auth или собственный identity provider для участников приложения.
6. Подключить `AdminDashboard` к агрегатам `app_daily_metrics` и audit log.
7. Провести отдельный threat model перед включением direct client access.
